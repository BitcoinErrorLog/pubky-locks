# Pubky Locks Master Plan (v1)

This document defines a hardened, implementation-ready plan for Pubky Locks: an authorization layer that ties Bitkit and Pubky App together through Paykit receipts and other proof types, while keeping a clean path to optional end-to-end confidentiality (Cryptrees, Key Regression, envelope encryption).

---

## 1. Goals

- Enable commerce for content, digital goods, subscriptions, memberships, checkouts, ecommerce workflows, and app features.
- Make payment verification out-of-band via Paykit receipts generated by wallets like Bitkit.
- Support multiple lock types: payment, password, membership/tag credentials, puzzles, time windows, contracts, and more.
- Preserve portability: users can migrate homeservers while retaining unlock semantics.
- Keep confidentiality optional: Locks must work for plain content and encrypted content.
- Keep protocol minimal and auditable: simple schemas, deterministic encoding, short-lived grants.

---

## 2. Non-goals

- Locks is not a payment protocol and must not process funds.
- Locks is not a generalized programming language or arbitrary policy VM.
- Locks does not require Cryptrees, Noise, or any particular storage format.
- Locks does not attempt cryptographic atomicity between payment and delivery (best-effort, idempotent, auditable).

---

## 3. Layer Model

Layer A (Authorization) is the Locks core and is always present.

Layer B (Confidentiality) is optional and orthogonal. If content is encrypted, UnlockGrant can carry encrypted key material or a capability that yields key material.

```
+--------------------------------------------------------------+
|          LAYER B: CONFIDENTIALITY (Optional)                 |
|                                                              |
|  Cryptrees | Key Regression | Envelope Encryption | Plain     |
|                                                              |
|  Only when you need zero-trust storage. Not required.         |
+------------------------------+-------------------------------+
                               |
                               | UnlockGrant can carry key material
                               v
+--------------------------------------------------------------+
|            LAYER A: AUTHORIZATION (Locks Core)               |
|                                                              |
|  LockPolicy -> ProofBundle -> Verifiers -> UnlockGrant        |
|                                                              |
|  Universal glue. Works with any storage. Paykit integration.  |
+--------------------------------------------------------------+
```

## 4. Core Primitives

### 4.1 LockPolicy

A signed, versioned policy stored with (or referenced by) a resource.

#### Requirements (normative)

- A LockPolicy MUST be signed by the creator key (or a delegated policy key authorized by the creator).
- A LockPolicy MUST include a stable `lock_id`.
- A LockPolicy MUST encode logic as a canonical JSON AST (not a string expression).
- A LockPolicy MUST declare receipt binding requirements for payment criteria.
- A LockPolicy MUST declare which issuer keys are authorized to mint UnlockGrants.
- A LockPolicy SHOULD declare outputs, including optional encrypted content-key delivery.

#### Example (illustrative)

```json
{
  "v": 1,
  "lock_id": "c32:3yqk2k5k8p0s7q9d",
  "resource": "pubky://alice/pub/posts/abc123",
  "creator": "pk:ALICE",

  "criteria": [
    {
      "id": "pay",
      "type": "payment",
      "asset": "SAT",
      "min_amount": 50000,
      "merchant": "pk:ALICE",
      "window_sec": 86400,
      "receipt_must_bind": ["lock_id", "resource"]
    },
    {
      "id": "pwd",
      "type": "password",
      "kdf": {
        "name": "argon2id",
        "salt": "b64:...",
        "params": { "m": 65536, "t": 3, "p": 1 }
      },
      "hash": "b64:..."
    },
    {
      "id": "gold",
      "type": "tag",
      "tag": "member:gold",
      "issuer": "pk:ALICE"
    }
  ],

  "logic_ast": {
    "op": "OR",
    "args": [
      { "op": "ANY", "args": ["pay", "pwd"] },
      { "op": "ALL", "args": ["gold"] }
    ]
  },

  "anti_replay": {
    "proof_bundle_sig_required": true,
    "server_challenge": "optional",
    "receipt_idempotency": "lock_id+viewer"
  },

  "authorized_grant_issuers": [
    { "type": "homeserver_key", "pk": "pk:ALICE_HS1", "expires_at": 1739999999 },
    { "type": "homeserver_key", "pk": "pk:ALICE_HS2", "expires_at": 1739999999 }
  ],

  "outputs": {
    "on_success": [
      { "type": "grant", "mode": "pop", "ttl_sec": 3600 },
      {
        "type": "content-key",
        "when": { "resource_is_encrypted": true },
        "scheme": "cryptree",
        "scope": { "path_prefix": "/priv/posts/abc123/" }
      }
    ]
  },

  "sig": "ed25519:..."
}
```

#### Notes

- Password locks are inherently brute-forceable if the hash is publicly accessible. They are acceptable for low-stakes use cases with rate limits and optional server challenge.

### 4.2 ProofBundle

A viewer-submitted container of proofs that attempt to satisfy a LockPolicy.

#### Requirements (normative)

- A ProofBundle MUST include `lock_id`, `resource`, and `viewer`.
- A ProofBundle MUST include a viewer signature over a canonical encoding of the bundle.
- Each proof entry MUST reference a `criterion_id`.
- Payment proofs MUST include a Paykit receipt whose signed content binds to `lock_id` and `resource` (or to `policy_hash` and a declared `resource_class`).
- Implementations SHOULD support an optional `server_challenge` to harden replay resistance.

#### Example (illustrative)

```json
{
  "v": 1,
  "lock_id": "c32:3yqk2k5k8p0s7q9d",
  "resource": "pubky://alice/pub/posts/abc123",
  "viewer": "pk:BOB",
  "client_time": 1736784000,
  "server_challenge": "optional-b64:...",

  "proofs": [
    {
      "criterion_id": "pay",
      "type": "paykit",
      "receipt": { "...": "..." },
      "method_proof": { "...": "..." }
    }
  ],

  "sig": "ed25519:..."
}
```

### 4.3 Verifier Interface

A registry of criterion verifiers that validate proofs and return structured facts for the policy evaluator.

#### Requirements (normative)

- Verifiers MUST be selected by `criterion.type`.
- Verifiers MUST validate proof schema deterministically (reject unknown fields unless explicitly allowed).
- Verifiers MUST return `(ok, fields, reason)` where `fields` are safe facts consumed by the logic evaluator.
- VerificationContext MUST include `lock_id`, `resource`, `viewer`, `policy_hash`, and `now`.

#### Rust sketch (illustrative)

```rust
pub struct CriterionResult {
    pub ok: bool,
    pub criterion_id: String,
    pub fields: std::collections::HashMap<String, serde_json::Value>,
    pub reason: Option<String>,
}

pub struct VerificationContext {
    pub lock_id: String,
    pub resource: String,
    pub viewer: String,
    pub policy_hash: [u8; 32],
    pub now_unix: i64,
    pub server_challenge: Option<Vec<u8>>,
}

#[async_trait::async_trait]
pub trait CriterionVerifier: Send + Sync {
    fn criterion_type(&self) -> &'static str;
    fn schema_id(&self) -> &'static str;

    async fn verify(
        &self,
        criterion: &serde_json::Value,
        proof: &serde_json::Value,
        ctx: &VerificationContext,
    ) -> CriterionResult;
}

pub struct VerifierRegistry {
    verifiers: std::collections::HashMap<&'static str, Box<dyn CriterionVerifier>>,
}
```

### 4.4 UnlockGrant

A signed capability minted by the creator side (homeserver) after successful verification.

UnlockGrants are short-lived, viewer-bound, and policy-bound. They can also carry encrypted key material for optional confidentiality.

#### Requirements (normative)

- UnlockGrant MUST bind to `lock_id`, `resource`, `subject` (viewer), and `policy_hash`.
- UnlockGrant MUST have a short TTL via `expires_at`.
- UnlockGrant MUST include an idempotency binding, typically `receipt_hash`.
- UnlockGrant MUST be signed by an issuer key listed in `policy.authorized_grant_issuers` (or provably delegated by the policy signer).
- UnlockGrant SHOULD default to proof-of-possession (PoP) mode for non-transferable access.

#### Bearer vs PoP

- `mode = "bearer"`: grant is sufficient to access.
- `mode = "pop"`: each use requires a subject signature over request binding data.

PoP is recommended to reduce value of stolen grants.

#### Example (illustrative)

```json
{
  "v": 1,
  "grant_id": "b64:random",
  "lock_id": "c32:3yqk2k5k8p0s7q9d",
  "resource": "pubky://alice/pub/posts/abc123",
  "subject": "pk:BOB",
  "mode": "pop",
  "rights": ["read", "download"],

  "issued_at": 1736784100,
  "expires_at": 1736787700,

  "policy_hash": "sha256:...",
  "idempotency": { "type": "receipt_hash", "value": "sha256:..." },

  "outputs": [{ "type": "access" }],

  "issuer": "pk:ALICE_HS1",
  "sig": "ed25519:..."
}
```

#### Encrypted content-key output (illustrative)

```json
{
  "outputs": [
    {
      "type": "content-key",
      "scheme": "cryptree",
      "scope": { "path_prefix": "/priv/posts/abc123/" },
      "encrypted_key": "b64:...",
      "enc": { "type": "noise_session", "session_id": "..." }
    }
  ]
}
```

## 5. Canonical Encoding and Signatures

To avoid interop failures and signature ambiguity:

- All signed messages (LockPolicy, ProofBundle, UnlockGrant) MUST use a canonical encoding.
- Recommended: JSON Canonicalization Scheme (JCS) or an equivalent deterministic JSON encoding.
- Floats MUST be forbidden. All numeric values MUST be integers or strings.
- Byte strings MUST use base64 with explicit prefix `b64:` or `base64:`.

---

## 6. Paykit Receipt Binding (critical)

Payment proofs must not be replayable across unrelated locks.

Minimum requirement:

- The Paykit receipt that is signed by the payer/payee (or by the payment method) MUST include a commitment to:
  - `lock_id`
  - `resource` (or `resource_class`)
  - `merchant` (creator key) if not already intrinsic
  - `amount` and `asset`
  - optional `expires_at` or `window_sec`

This commitment MUST be covered by the receipt signature(s).

Recommended data:

- `lock_commitment = H("pubky-locks-v1" || lock_id || resource || merchant || amount || asset)`

The LockPolicy should state what binding is required via `receipt_must_bind`.

---

## 7. Issuer Keys and Delegation

Problem: a random server key must not be able to mint valid grants for Alice.

Solution:

- LockPolicy declares `authorized_grant_issuers`, a list of issuer keys allowed to sign UnlockGrants.
- Clients MUST verify the grant signature and MUST verify that the `issuer` key is authorized by the policy.
- If delegation is used instead of explicit listing, the policy MUST define delegation proof format (not required for MVP).

MVP recommendation:

- Explicit listing of homeserver issuer keys with an expiration time.

---

## 8. Anti-replay and Idempotency

### 8.1 Idempotency

- Homeserver MUST store `idempotency_key` for successful unlocks.
- Default: `idempotency_key = H(lock_id || viewer || receipt_hash)` for payment-based unlocks.
- On duplicate submission, server MUST return the same result or a stable equivalent (same grant or a refreshed grant with same semantic rights).

### 8.2 Optional server challenge

- Server MAY require a challenge to be included in ProofBundle.
- If used, challenge MUST be short-lived and bound to (lock_id, viewer).

This is primarily useful for password locks and other non-payment proofs.

---

## 9. Grant Usage Binding (PoP mode)

When `mode = "pop"`, the client must include a per-request signature that binds:

- grant_id
- method (READ, GET)
- canonical request path
- server-provided nonce (optional) or client timestamp

A simple pattern:

- Client sends `Authorization: PubkyGrant <grant_b64>`
- Client sends `Grant-POP: <b64(signature over pop_payload)>`
- pop_payload = canonical JSON:
  - { grant_id, method, path, ts, nonce? }

Server verifies subject signature using `grant.subject` key.

## 10. Protocol Endpoints and Flow

### 10.1 Discovery

Client fetches a resource.

If locked, server returns an envelope indicating:

- lock_required = true
- lock_policy_ref (URI or path)
- optional `challenge` if configured

### 10.2 Verify

Client submits ProofBundle to:

- `POST /.well-known/locks/verify`

Response:

- success: UnlockGrant
- failure: structured error with which criteria failed

### 10.3 Access

Client requests the resource with:

- `Authorization: PubkyGrant <base64(grant)>`
- If PoP: include per-request POP signature header

If encrypted:

- Client obtains encrypted key output from grant and decrypts locally.
- Resource body can remain ciphertext, or server can return ciphertext by default for encrypted resources.

## 11. Confidentiality Layer (optional)

### 11.1 Cryptrees

Use Cryptrees when you need zero-trust storage confidentiality.

- Content is stored encrypted.
- Access is granted by sharing a subtree key (parent key) or a specific data key.
- UnlockGrant outputs can deliver key material encrypted to the viewer via Noise session or sealed encryption.

Recommended delivery:

- Use an existing authenticated pubky-noise channel to deliver keys.
- Store minimal key references on server; do not store viewer private keys.

### 11.2 Envelope encryption (single asset)

For simple encrypted blobs:

- Creator encrypts content with a random DEK.
- UnlockGrant delivers DEK encrypted to viewer.

### 11.3 Key Regression (subscriptions, episodic releases)

Key regression is useful for periodic content where membership buys future releases.

- UnlockGrant outputs can deliver `member_state` (stmX) which enables deriving future keys.
- Not a general Locks foundation, but valuable as an output scheme for certain lock types.

---

## 12. Biscuit Profile (optional serialization)

Biscuit is not required for Locks core.

Use Biscuit only when you need:

- Attenuation (delegation) in marketplaces, affiliates, ecommerce platforms
- Third-party facts injected into proofs or grants
- Edge evaluation outside the origin homeserver

Guidance:

- Keep UnlockGrant as the core internal representation.
- Provide a separate adapter that encodes the grant as a Biscuit token when needed.
- Revocation is achieved via short TTL plus server-side checks when applicable.

## 13. Implementation Roadmap

### Phase 1: MVP (Locks core + Paykit bridge)

Goal: Password + Paykit receipt unlock, tying Bitkit to Pubky App.

Deliverables:

1. LockPolicy schema (JSON, JCS, Ed25519 signing)
2. ProofBundle schema (JSON, JCS, Ed25519 signing)
3. UnlockGrant schema (JSON, JCS, Ed25519 signing)
4. Policy logic evaluator over `logic_ast`
5. PaymentVerifier that validates Paykit receipts + method proofs
6. PasswordVerifier (argon2id) with rate limits and optional challenge
7. Homeserver endpoint:
   - `POST /.well-known/locks/verify`
8. Idempotency store keyed by receipt_hash and viewer
9. Pubky App UX:
   - locked indicator
   - show policy
   - hand off to Bitkit for payment
   - paste/import receipt
   - obtain grant and view content

### Phase 2: Tags and memberships (subscriptions)

Goal: Membership locks, revocation, expiring credentials.

Deliverables:

1. Tag credential format (Ed25519 signed)
2. TagVerifier
3. Revocation lists:
   - policy references a revocation source
4. Subscription integration:
   - subscription proof produces a tag credential with expiry
5. Issuance endpoints (optional; not required if tags are minted elsewhere):
   - `POST /.well-known/locks/tags/issue`
   - `POST /.well-known/locks/tags/revoke`

### Phase 3: Extended verifiers

Goal: Expand lock types.

Deliverables:

- PuzzleVerifier (deterministic KDF proof or PoW)
- TimeVerifier (before/after windows)
- ContractVerifier (multi-party signatures)
- Defer GeoVerifier until a credible attestation story exists

### Phase 4: Confidentiality layer

Goal: Zero-trust content protection for private goods and content.

Deliverables:

- Cryptree client library
- UnlockGrant `content-key` outputs
- Noise-based key delivery integration (pubky-noise sessions)
- Optional Key Regression output mode for release streams

### Phase 5: Advanced commerce

Goal: Delegation, marketplaces, affiliates.

Deliverables:

- Biscuit adapter profile for UnlockGrant
- Delegation patterns:
  - marketplace attenuates creator grant
  - affiliate/checkout tokens
- Third-party verifier allowlisting and facts

---

## 14. Testing and Interop

- Provide test vectors for:
  - canonical JSON encoding and signatures
  - policy_hash computation
  - receipt binding commitments
  - logic_ast evaluation correctness
  - PoP request binding verification
- Fuzz parsers for logic_ast and schema validation.
- Ensure strict rejection of unknown fields in signed objects unless explicitly allowed.

---

## 15. Versioning

- Each primitive includes `v`.
- Introduce new versions only when necessary, and keep v1 stable.
- `policy_hash` should include `v` and all signed policy fields.

---

## 16. Summary

Locks v1 is an authorization layer with four primitives:

- LockPolicy: signed policy attached to a resource
- ProofBundle: viewer signed proof container
- Verifiers: deterministic proof checks producing facts
- UnlockGrant: short-lived capability bound to viewer, resource, and policy

Confidentiality remains optional, delivered via UnlockGrant outputs when needed. Biscuit remains optional for advanced delegation, not required for the core system.
